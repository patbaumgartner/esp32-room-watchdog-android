# ADR-0001: Release Signing and GitHub Releases Distribution

- **Status:** Accepted
- **Date:** 2026-11-14
- **Deciders:** Patrick Baumgartner

## Context

The app was buildable from source (`assembleRelease` produced an unsigned
APK), but nothing was published: the repository had no release workflow, no
tags, and no releases, so users had no way to download an installable APK
from the GitHub Releases page. An unsigned or ad-hoc-signed APK cannot be
updated in place (Android rejects updates signed with a different key), so a
stable release key is required before the first public build.

Options:

1. **Publish unsigned APKs** — rejected: Android refuses to install an
   unsigned APK, and debug-signed builds cannot update over each other.
2. **Sign in CI with a key generated per run** — rejected: every build would
   have a different signature, so no update path exists between builds.
3. **One stable release key, stored only as repository secrets, used by a
   release workflow for both releases and snapshots** — chosen.

## Decision

- **Distribution:** `.github/workflows/release.yml` publishes to the GitHub
  Releases page:
  - every push to `main` rebuilds the **Snapshot** prerelease
    (tag `snapshot`) with a signed APK (`room-watchdog-snapshot.apk`) and
    `SHA256SUMS`;
  - every push of a tag `vX.Y.Z` creates a release with a signed APK and a
    signed AAB (`room-watchdog-<version>.apk` / `.aab`, for Play-style
    distribution), `SHA256SUMS`, install instructions, and the signer
    certificate fingerprint. The tag sets `versionName` (`v0.1.0` → `0.1.0`)
    and `versionCode` (`major*10000 + minor*100 + patch` → `100`); snapshot
    builds use `versionCode = 2_000_000_000 + run_number` so they always sort
    above any tag-derived code and can update over releases.
- **Signing key:** a single PKCS12 keystore (RSA 2048, alias
  `room-watchdog-release`, 30-year validity) generated by the maintainer. It
  exists only as the repository secrets `SR_KEYSTORE_BASE64`,
  `SR_KEYSTORE_PASSWORD`, `SR_KEY_ALIAS`, `SR_KEY_PASSWORD` (base64-encoded
  keystore plus passwords) and in one offline backup outside the repository.
  It is never committed; `.gitignore` already excludes `*.jks`, `*.keystore`,
  `*.p12`, `keystore.properties`. Signer certificate SHA-256:
  `7B:38:EA:6A:1B:4B:86:26:A0:38:41:21:C6:A2:16:4E:00:14:68:F2:F0:A8:9D:AA:47:BC:1B:73:87:41:87:BB`.
- **Build wiring:** `app/build.gradle.kts` reads the credentials from the
  `SR_KEYSTORE_FILE` / `SR_KEYSTORE_PASSWORD` / `SR_KEY_ALIAS` /
  `SR_KEY_PASSWORD` environment variables (CI) or a local, git-ignored
  `keystore.properties` file, and attaches the `release` signing config only
  when they are present — a plain source checkout still builds an unsigned
  release APK. The five `DEV_*` debug prefill fields stay empty in release
  builds regardless. `versionName` / `versionCode` can be overridden with
  `-PversionName=…` / `-PversionCode=…`.
- **Verification:** the workflow runs `apksigner verify --print-certs` on the
  APK before publishing and fails if the signing secrets are missing; users
  can verify downloads against the published `SHA256SUMS` and the
  certificate fingerprint in the release notes.

## Consequences

- Users can download and install the APK directly from the Releases page;
  releases and snapshots share one key, so they update in place.
- The release key is a single point of failure: the offline backup must be
  kept safe (password manager / HSM). Losing it means future updates cannot
  be signed with the same key and users would have to reinstall. Key
  rotation requires re-signing and a documented migration.
- The workflow needs `contents: write` only in the two publishing jobs; the
  default token permissions stay `contents: read` everywhere else.
- Secrets must be set before the first release run; the workflow fails fast
  with a pointer to `CONTRIBUTING.md` if they are missing.
